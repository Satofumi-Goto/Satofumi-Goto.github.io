# 改訂ログに「書くか」の判定基準

**更新日は変更があれば必ず自動で進める。本文(箇条書き)は、下の基準で客観的に評価し、基準を満たす場合だけ書く。**
評価は「そのカードに既に記載している項目」を基準にした相対評価で行い、結果は全件 `decisions.jsonl` に残す（書かない判断も記録する）。

## 1. 評価単位
同じ目的の変更(PR・コミット)をひとまとめにして1件として採点する。対象期間は、カードの `reviewed_at` 以降。

## 2. 採点（合計10点）
| 観点 | 3 / 2 / 1 / 0 |
|---|---|
| 新規性 (0–3) | 3=既存項目にない種類の機能・成果／2=既存項目の範囲を明確に拡張／1=既存項目の細部の追加／0=既存項目に含まれる |
| 規模 (0–3) | 3=主要画面・主要数値・公開物の構造が変わる／2=1つの機能の挙動が変わる／1=軽微／0=内部のみで外から見えない |
| 検証可能性 (0–2) | 2=公開物・アプリで第三者が確認でき、件数や数値で示せる／1=説明のみ／0=示せない |
| 既存記述への影響 (0–2) | 2=既存の項目が事実と食い違う(修正が必須)／1=既存項目の裏付けを強める／0=影響なし |

## 3. 判定
- **記載する**：合計6点以上、かつ「新規性2以上」または「既存記述への影響2」。
- **必ず修正する**：「既存記述への影響」が2（既存の記載が事実と違ってしまう）なら、点数に関係なく該当項目を直す。
- **記載しない**：上記以外。日付だけ進める。
- **常に対象外**：挙動が変わらないリファクタ、依存パッケージの更新、文言・体裁・誤字の修正、テストやCIの追加のみ、内部名称の変更。
  ただし既存項目に件数や数値があり、それが変わる場合は「既存記述への影響」で評価する。

## 4. 書き方
- 事実だけを書く。公開物・アプリ・リポジトリで確認できない数値や成果は書かない。誇張しない。
- 計画シナリオの値を運行実績と誤読させない（既存の注記を保つ）。
- 1カードの項目は最大10。超える場合は、最も点数の低い既存項目と統合または置換する。
- 英語ページは英語、`/portfolio/` は日本語。同じカードは全ページで同じ内容にする（`revisions.json` の `en` / `ja` を同時に更新）。
- 見出しに「9月以降」などの期間は書かない。
- 新しいカードは作らない。

## 5. 記録
`decisions.jsonl` に1件1行で、`at`（時刻）、`card`、`changes`（PR番号やコミット）、`scores`、`verdict`（written / corrected / skipped）、`reason` を追記する。
