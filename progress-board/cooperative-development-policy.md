# Seneschal／Federation 開発協調チーム 共通指示書

最終更新：2026-11-05。対象：Seneschal、Federation、Simulator、Activityおよび各独立コンソール。既存の開発オーケストレータ（毎時）に適用する。**本書は `progress-board/orchestrator-policy.json` のrelease freeze、CI/quota、承認・公開ゲートに従う補助的な作業規程であり、その安全基準を緩和しない。**

## 1. 目的・原則

PRを増やすことではなく、未完了案件を減らして製品を完成させる。全員を機能・工程別に固定しない。各担当は最新mainの調査、原因特定、最小差分実装、テスト、PR、独立レビュー、マージ条件の確認、公開前QA、ユーザー公開後の実画面検証、旧PR整理まで案件単位で責任を持つ。

## 2. 体制と実在性

- 既存の開発オーケストレータ：1。優先順位、競合、引継ぎ、品質、費用・実行回数を調整する。
- 対等な協調開発担当：最大4枠（co-dev-01〜04）。上下関係や恒久的な専属工程は設けず、案件ごとに主担当1名を宣言する。残りは調査・レビュー・テスト・修正提案を支援できる。
- 既存専門担当：必要時のみ参加する。
- **枠は実行中の独立エージェントを意味しない。** 実際に利用可能な実行環境・担当者だけをアクティブと記録する。未接続の枠を稼働済みと報告しない。担当が停止した場合、別の利用可能な担当へ引き継ぐ。
- 同じ監視の定期ジョブを追加しない。既存の毎時オーケストレータを維持する。

## 3. 共通台帳と案件取得

既存GitHubの **Issueを案件原簿**、**PRを変更・レビュー原簿**、`progress-board/status.json` を全体状況の表示・集計台帳とする。並行する別正本を作らない。既存の17 owner rowsを破壊しない。

案件着手時に最新のpolicy、GitHub main、Issue、open PR、変更対象ファイル、他担当の宣言を読む。Issueに以下を追記・更新し、台帳には参照を残す：

```text
issue/repo: ...
primary: <担当識別子 or 未割当>
helpers: ...
state: unclaimed | claimed | implementing | review | ci_blocked | approval_blocked |
       ready_for_owner_publish | owner_published_qa_pending | verified_done | blocked
base_main_sha: ...
branch/pr: ...
planned_files: ...
overlap_and_dependency: ...
next_action_and_handoff: ...
evidence_urls: ...
```

同一Issueの主担当は同時に1名とする。宣言後も着手直前に競合を再確認し、他者の宣言と衝突したら変更せずHOLDする。コメントだけを排他ロックと見なさない。GitHubで競合なく取得・更新できたことを再確認する。曖昧な状態で同じファイルを編集しない。

## 4. 共通の実装工程

1. main、既存Issue/PR、CI、公開SHAと既存実装を確認する。
2. 未完了・重複・旧仕様・停滞案件を洗い出す。
3. 対象Issueへ主担当、協力者、予定変更ファイル、依存・競合を宣言する。
4. 最新mainから `feature/*` 等の専用ブランチを作り、作業ツリーがcleanであることを確認する。
5. 最小差分で修正する。全文上書き、format-all、無関係差分、main直接更新は禁止。
6. 静的検証・対象テスト・必須CI・実ブラウザQAを行い、実行した内容と未実施を区別する。
7. PRを作り、作成担当とは別の有効なレビュアーを要求する。CIの代わりにレビュー、レビューの代わりにCIを使わない。
8. CI・独立レビュー・保護条件が全部満たされた場合のみmainへ統合する。
9. 公開前QAと公開待ちを記録し、ユーザー本人によるPublish／Deploy／DNS切替を待つ。
10. 公開後に実SHA、JS/CSS、環境、API、Map・Calendar・予約・配車・親子コンソール連携、スクリーンショットで再確認する。
11. 旧PRを理由・証拠付きで整理し、履歴とIssueを更新する。
12. 全完了条件に合格したときだけ `verified_done` としてIssueを閉じる。

## 5. PR分類と処理

| 分類 | 処理 |
| --- | --- |
| 必要・競合なし | 必須CI・独立レビュー・保護条件の合格後に統合 |
| 必要・競合あり | 既存PR修正か最新mainへの差分移植を比較し、再検証 |
| 実装済み・重複 | mainに実在する証拠と元PRへの参照を記録してクローズ |
| 旧仕様・不要 | 不採用理由・影響・代替案を記録してクローズ |

ブロック中PRはブロック理由、解除条件、次アクション、引継ぎ先を記録する。**PR作成・main統合は案件完了ではない。**

## 6. 競合・安全・費用

- 保護対象：App、Router、Provider、Google Maps、認証、支払い、秘密鍵、データ削除。変更理由・root cause・影響・復帰手順を明示し、必要承認がない場合は止める。
- Seneschal Mapの過去の再発防止：`functions/getGoogleMapsApiKey.js` の配置、Google Mapsの非同期ロード待ちと再試行、地図の選択場所表示の既存契約を壊さない。
- Base44 AI開発指示、同じ機能のBase44/独立環境二重実装、秘密値の閲覧・出力、危険な強制同期は禁止。
- `quota_blocked` 中はGitHub Actionsの無意味なリトライや費用のかかるブラウザ/API検査を繰り返さない。CIが走らなかった場合は成功と扱わず、静的検証とHOLD理由を記録する。
- 他担当のPRがmainへ統合されたら、その都度branchとの差分・変更ファイルを再点検する。
- 既存オーケストレータの `max_primary_change_per_repo` と `max_queue_items` を尊重する。担当が複数いても同一repoで危険な並行編集を増やさない。

## 7. 公開の境界と完了定義

**本番Publish／Deploy／DNS切替、公開ワークフロー実行、自動リリースはユーザー本人専任。** 開発担当はコード・PR・CI・マージ・公開前QAまで行い、公開後は読み取りと実画面検証を行う。独立ステージングの例外も既存policyの凍結・費用・明示ゲートを満たす場合に限る。

完了には、①main統合 ②必要CI・独立レビュー ③旧PR整理 ④ユーザー公開完了 ⑤配信SHA/JS/CSS/APIと実ブラウザQA・スクリーンショット ⑥証拠・変更履歴 ⑦回帰不具合なし、の全てが必要。公開待ちは `ready_for_owner_publish` として開いたままにする。ステージングのみ成功と本番完了を混同しない。

## 8. 引継ぎと通知

停止・交代時はIssue／PR／ブランチ／変更ファイル／最終main SHA／未完了テスト／承認待ち／公開待ち／次の一手を残す。オーケストレータは必要なら次の利用可能な担当へ引き渡し、担当の細かな承認待ちを発生させない。重要な進展、障害、本人しかできない操作だけ通知する。変更がない回は重複報告・重複実行を避ける。

**最終原則：主担当は案件完遂に責任を持つ。全員は協力できるが、未設置の担当・未実施の検証・未公開の機能を「完了」とは言わない。**
