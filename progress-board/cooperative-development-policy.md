# Seneschal / Federation 協調開発チーム 共通運用ルール

版: 2026-11-05  
適用範囲: Seneschal、Federation、Simulator、各独立コンソール  
運用元: 既存の毎時「開発オーケストレータ」。同一監視を行う定期ジョブを新設しない。

## 最終目的

担当者の成果はPRの作成件数ではなく、未完了案件を実運用上で完遂し、回帰不具合なく閉じること。全員は固定的な機能担当・工程担当ではなく、調査、実装、検証、PR、統合準備、公開前・公開後の検証を遂行できる同等の開発担当として協力する。

## 体制・責任

- 開発オーケストレータ1、協調開発担当3〜4、必要に応じ既存専門担当。実際に稼働する担当は接続・稼働証跡を確認すること。未接続担当を稼働済みと報告しない。
- 案件ごとに主担当1名を一時的に置く。他担当は原因調査、レビュー、テスト、修正提案に協力する。
- オーケストレータは優先順位・衝突・停滞・CI/公開状況・コスト・完了証跡の調整役とし、担当が自力で処理できる工程の細かな承認を要求しない。
- 主担当が停止した場合は他担当が引き継ぐ。引継ぎにはIssue、PR、ブランチ、直近main SHA、変更ファイル、未実施テスト、阻害要因、次の1アクションを必ず明記する。

## 着手前の共有台帳と衝突防止

- 最初にGitHub最新main、既存Issue/PR、直近の変更ファイル、進捗台帳 `progress-board/status.json`、最新の `progress-board/orchestrator-policy.json` を読む。後者のrelease_freeze、CI quota、公開/課金ゲートが優先。
- GitHub Issueを案件単位のclaim/ハンドオフ記録の正本とし、`status.json`は全体状況の集計に使う。既存IssueがあればそのIssueへ記録し、同じ案件のIssueやPRをむやみに増やさない。
- 着手宣言の最小項目: issue URL、repo、主担当、協力担当、作業状態、main SHA、関連PR、対象ファイル、依存/衝突、次の検証。重複着手の疑いがあれば変更前に再照合する。
- 担当が別々に同一ファイルを無秩序に書き換えない。他担当のPRがmainに入った後は差分を再比較し、PRの内容と実テストを更新する。

### 案件の流れ

1. 最新mainとIssue/PRを確認し、未完了、放置、競合、重複、既実装を分類。
2. 既存PRがある場合はそれを修正するか、最新mainから差分を移植するか比較し選択。
3. 共通Issueに主担当・対象ファイル・既存PR・ブロックを宣言。
4. クリーンな作業領域・最新mainを確認後、専用featureブランチを作成。
5. 保護対象と依存関係に注意して最小限の差分のみ実装。全文rewrite、format-all、main直接編集は禁止。
6. 対象テスト、静的検証、必要なCI、実ブラウザQAを実施し、変更ファイルとdiffを提出。
7. PRを作成し別担当レビューを受け、保護・CI・承認条件が満たされた場合のみmainへ統合。
8. 公開前QAと公開手順を検証して、公開操作を要する場合は所有者への引継ぎ状態にする。
9. ユーザー本人が本番Publish/Deploy/DNS切替を行った後、公開SHA、配信JS/CSS、API、実画面とスクリーンショットで検証。
10. 関連旧PR・Issueを整理し、証拠付きで完了/未完了を台帳に記録。完了担当は次の優先案件を取得。

## PR分類と処理

| 区分 | 次の対応 |
| --- | --- |
| 必要・競合なし | 必須CI、別担当レビューと保護条件を満たしてマージ |
| 必要・競合あり | 最新mainへ差分を移植、影響を再テストしレビュー |
| 実装済み・重複 | main・機能・テストの証拠を記録して旧PRをクローズ |
| 旧仕様・不要 | 採用不要の理由、代替先、影響を記録してクローズ |

保留PRには必ず阻害理由、必要条件、責任担当、次の具体アクションを記載する。ソース統合済みでも本番公開・実機検証待ちは「完了」にしない。

## 安全境界

- GitHub mainがコードの唯一の正本。mainへ直接writeしない。
- Base44 AIへの開発指示や全文上書きは禁止。Base44版と独立版へ同一変更を二重実装しない。
- App、Router、Provider、Google Maps/Mapの保護対象を無承認変更しない。差分・依存・回帰を事前確認する。特にGoogle Mapsのキー返却関数配置、非同期ロード完了待ち、MapPage再試行を壊さない。
- CI失敗・quota_blocked・承認不足・draft・conflictを迂回しない。失敗を同じ条件で無駄に再実行しない。レビュー要件の代替を自己承認で偽装しない。
- データ削除、秘密鍵、認証・権限、課金・外部有料API、不可逆操作を勝手に実施しない。
- 利用者の個人情報やsecret値はIssue/PR/ログへ記録しない。
- 既存の7アプリ公開順と独立環境の認証・E2E・費用ゲートを維持する。

## 本番公開境界・QA

開発担当はコード調査、修正、PR、CI、レビュー、承認ゲート適合のマージ、公開前QAまで担当する。**本番Publish/Deploy、DNS切替、公開workflow起動はユーザー本人のみ**。独立ステージングの既存の別途許可済み運用があっても、本番と混同しない。

公開後は最低限以下を別々に判定する。

- 公開バージョンSHAとレビュー済main/リリース基準の整合。ソース統合と公開一致を区別する。
- 配信JS/CSSの実バイト整合、正しいオリジン・実行環境・API/認証/DB接続。
- Map、Calendar、予約、配車、自動運行、コンソール連携、Federation親子接続の対象実画面。
- 実ブラウザ操作と対象ページのスクリーンショット、Changed Files、テスト/CI/レビュー・公開証跡。
- 既存機能の回帰不具合がないこと。正常を示せない項目は未検証。

## 完了判定（all required）

- 必要コードがmainにマージ済み。
- 必須CI・別担当レビュー・保護条件に合格。
- 関係する旧PRを理由付きで整理。
- 必要なユーザー本番公開が完了。
- 対象の公開後実画面/E2E/スクリーンショット検証に合格。
- 証拠、変更履歴、回帰テスト結果が残る。

公開待ち、認証不足、外部依存、CI quota_blocked は `source_integrated` または `blocked` と明示し、`complete` と混同しない。オーケストレータは新事実がない場合に重複ログ・ジョブ・高コストAPI呼出しを増やさない。

**最終原則: PRを増やすために開発しない。重複せず協働し、最後の本番受入れまで責任を持ち、未完了案件を減らす。**
